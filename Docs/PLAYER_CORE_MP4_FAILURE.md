# 2.2.9（47）：MP4 验证失败修正

用户反馈：其他视频正常，一条 MP4 HDR 视频硬解和软解均失败；46 版诊断显示目标约 649.646 秒，错误 -1094995529。

固定的 FFmpeg 8.0.2 `libavutil/error.h` 将此值定义为 AVERROR_INVALIDDATA（输入数据处理失败），不能只凭此码断定网络超时、文件损坏或 HDR 不支持。46 版 Swift 在发布最终快照之前停止会话，所以其 0 帧/等待媒体信息可能是过期的诊断，不能当成准确的失败阶段。没有取得该私人视频，以下代码修正仍需用户真机验收。

## 修正

- 失败发生处记录明确阶段：打开、探测、选轨、视频初始化、定位、读包、视频解码或像素转换。最先发生的错误保留，不被另一线程或软件恢复覆盖。
- 探测后立即保留已知的容器、codec、profile、轨道、分辨率和源色彩信息，即使后续初始化失败。Swift 在停止前同步发布最终快照，复制诊断包含错误文本/代码，不只保留通用提示。
- 无声验证入口的音频初始化/解码错误改为明确警告并跳过该音轨的验证，视频验证继续。此策略只用于当前无声验证，并非正式音频支持或下一阶段音频故障处理方案。
- 视频选择排除 attached-picture 封面轨；FFmpeg `av_find_best_stream` 本身并不排除这一类轨道。
- 仅在媒体探测 INVALIDDATA 或视频参数不完整时，用新 demuxer 扩展探测一次（2 MiB/3 秒 → 8 MiB/8 秒）；普通视频没有新增探测等待。打开地址失败、网络错误和取消不进行此类重试。
- 恢复播放明确使用所选视频轨的 time base 定位，失败时在同一 I/O 时间上限内尝试一次旧 keyframe seek API。去掉成功 seek 后多余的 `avformat_flush`，避免再清除 seek API 内部刚准备的队列。不会自动从头下载/解码 649 秒来伪装定位成功。
- 新增“解码器实际输出帧”和“目标前预滚帧”，区分没有解码输出与尚未到目标时间。失败页提供“从头验证”，用于检查定位路径与从零开始是否有差异。

## 交付与验证边界

源码 preflight、Bash 语法、diff 检查；实际 FFmpeg C / Swift 构建、链接与 IPA 打包由 GitHub macOS 执行，见对应提交的工作流结果。未新增 regression 脚本、作业或产物。Windows 没有执行真机视频验证。

真机：先直接进入验证（保留约 649 秒的恢复位置）；如仍失败，先复制完整诊断，再点“从头验证”并复制其结果。检查已能正常播放的视频、暂停/拖动、退出与重新进入。日常 AVPlayer/VLC、115 登录/文件浏览及缩略图逻辑未修改。

依据：[FFmpeg 8 的 demux/seek API](https://ffmpeg.org/doxygen/8.0/group__lavf__decoding.html)，并核对仓库内固定 8.0.2 源码包的 `avformat.c`、`seek.c`、`error.h`。
